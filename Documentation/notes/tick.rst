=============
1 ms 系统节拍
=============

**系统节拍** (system tick) 是定时器按固定周期产生的中断, 内核以该中断为时间基准. Leonix 的节拍周期为 1 ms, 即 HZ 为 1000, 由 arch/avr/time.c 配置的
Timer1 产生. 节拍由提交 104f2cc (2026-10-08) 加入, d4fcdd3 把中断向量移入
switch.S, 节拍本身的配置此后未变.


为什么需要节拍
==============

没有节拍时, 程序只能用延时循环计时, 即让 CPU 空转固定的次数. 这种计时依赖
每条指令的周期数, 而且计时期间 CPU 无法执行其他工作. 节拍把当前时间变成一个由
硬件推进的计数器 jiffies, 任何代码都可以读取, 读取本身只需几条指令.
调度器 (scheduler.rst) 也借用同一个中断, 每个节拍切换一次任务.


周期的计算
==========

Timer1 是 16 位计数器. time_init() 把 Timer1 配置为 **CTC 模式** (Clear Timer on
Compare Match, 数据手册 14.8.2 节): 计数器每个定时器时钟加 1, 等于 OCR1A 时
置位比较匹配标志并触发中断, 下一个时钟回到 0.

CPU 时钟为 16 MHz, 经 64 分频后作为定时器时钟::

  定时器时钟   16000000 / 64   = 250000 Hz, 每个时钟 4 微秒
  每个节拍     250000 / 1000   = 250 个定时器时钟
  OCR1A        250 - 1         = 249

减 1 的原因是计数器从 0 数到 249, 共经过 250 个值. time.c 中 TIMER1_TOP
的定义就是这一算式. 两条 ``_Static_assert`` 在编译时检查时钟能否被整除, 否则节拍周期不是整数个定时器时钟, 以及结果能否放进 16 位的 OCR1A.

分频系数写作 ``64UL`` 而不是 ``64``, 是因为 AVR 上的 int 只有 16 位,
``64 * 1000`` 等于 64000, 超出 int 的上限 32767. 提交 104f2cc 第一次编译时,
这一溢出由 ``-Werror=overflow`` 报出.

CTC 模式下计数器由硬件归零, 与中断何时得到处理无关. 若改用普通模式, 在中断
处理程序中把 TCNT1 写回 0, 从比较匹配到这次写入之间计数器已经前进的值会被
丢弃, 而这段延迟随中断响应的时机变化, 节拍周期因此不再精确. Caterina 的
Timer1 采用的是后一种写法.


寄存器的写入顺序
================

time_init() 按下列顺序写入::

  TCCR1B = 0;                      停止计时器
  TCCR1A = 0;
  TCNT1 = 0;
  OCR1A = TIMER1_TOP;
  TIFR1 = 1 << OCF1A;              清除挂起的比较匹配标志
  TIMSK1 = 1 << OCIE1A;            允许比较匹配 A 中断
  TCCR1B = (1 << WGM12) | (1 << CS11) | (1 << CS10);
                                   CTC 模式, 64 分频, 开始计数

先停止、最后启动, 配置过程中计数器不会运行. TIFR1 一行往往使初学者困惑:
向中断标志位写 1 是清除该标志, 写 0 没有作用 (数据手册 14.10.19 节). 若之前
留有挂起的标志, 中断一打开就会立即进入一次处理程序.

time_init() 运行时 SREG 的 I 标志仍然清除, 因为 start.S 已把 SREG 清零,
而第一次打开中断发生在 sched_start() 进入第一个任务时的 ``reti``. TCNT1
与 OCR1A 是 16 位寄存器, 需要分两次写入, 中断关闭时这两次写入不会被打断.


jiffies
=======

每个节拍, timer_interrupt() 把 32 位变量 jiffies 加 1. 这个名称沿用自
Linux 内核.

jiffies 被声明为 ``volatile``. 该变量在中断中被修改, 在任务中被读取, 编译器
看不到中断与任务之间的关系. 不加 ``volatile`` 时, 编译器可以假定一个循环
里反复读取的值不会改变, 把读取移出循环, 任务因而永远无法观察到时间到达.

AVR 一次只能读取 8 位, 读取 32 位的 jiffies 需要 4 条 ``lds`` 指令, 节拍
中断可能落在其中两条之间. 设 jiffies 从 0x0000ffff 变为 0x00010000, 而
中断恰好发生在读完低 2 字节之后: 读到的低 2 字节是 ffff, 高 2 字节是 0001,
拼成 0x0001ffff, 比真实值超前约 65.5 秒. get_jiffies() 因此在
``ATOMIC_BLOCK`` 中读取. 该宏先保存 SREG 并关闭中断, 读完之后恢复 SREG.

32 位的 jiffies 在 HZ 为 1000 时约 49.7 天回绕到 0. 比较两个时刻时,
``time_after_eq()`` 计算两者之差, 再把差按有符号数判断正负. 设截止时刻为
0xfffffff0, jiffies 回绕之后读到 0x00000005. 直接比较 ``now >= deadline``
得到假, 实际上截止时刻已过去 21 个节拍; 两者之差 0x15 按有符号数是 21, 为
正, 结果正确. 只要比较的两个时刻相距不足 2^31 个节拍, 约 24.8 天, 这一
写法在回绕前后都成立.


实测
====

104f2cc 的映像为 556 字节. 2026-10-08 上电之后, L LED 以 0.5 秒的间隔翻转.
该间隔完全由节拍中断推进的 jiffies 决定, 因此 1 ms 节拍、弱符号向量的覆盖
与 ``.data`` 的复制同时得到确认 (提交 b56d672). 间隔为目测结果, 未用仪器
计时.
