======================
字符设备、终端与 shell
======================

**shell** 是读取命令行并执行命令的程序. Leonix 的 shell 运行在 USB 串口
ttyACM0 上, 用于在板子运行时查看任务状态、栈余量与内核日志. shell 之下有
两层: 字符设备表提供与具体驱动无关的读写入口, 终端行规程把逐键到达的输入
整理成行. 代码在 fs/char_dev.c 与 drivers/tty.c, shell 本身是
leonix-coreutils 中的 /bin/sh.


使用
====

在电脑上用终端程序打开串口, 例如::

  screen /dev/cu.usbmodem101

打开时先回放内核日志, 随后出现提示符 ``#``. 命令是 /bin 下的程序,
``ls /bin`` 列出全部程序, 见 vm.rst. 其中 ``ps`` 每个任务
一行: 编号、状态与栈余量. 状态的字母取自 Linux 的 ps: R 可运行, S 睡眠
(等待时间或事件), B 阻塞, D 已结束. 最后一行 ``id`` 是空闲任务.

``screen`` 中按 Ctrl-A, 再按 K 并确认, 即可退出. 终端关闭之后再次打开,
提示符不会重新出现, 按一次回车即可.

直接关闭终端窗口时, screen 并不退出, 而是转入后台 (detached) 并继续占用
串口, 之后再执行 screen 或 make flash 都会因端口被占用而失败. ``screen -ls``
列出后台会话, ``lsof /dev/cu.usbmodem101`` 列出占用串口的进程,
``screen -X -S 会话号 quit`` 结束该会话.


字符设备
========

Linux 中设备以**字符设备** (character device) 的形式出现, 程序通过
``struct file_operations`` 中的 ``read`` 与 ``write`` 读写设备, 不必知道
驱动的内部. Leonix 沿用这一接口 (提交 84e0b53), 去掉了文件与偏移: 每个设备
在两个方向上各只有一个字节流.

Linux 以主、次设备号登记字符设备, 程序经由 /dev 下的设备节点得到设备号.
Leonix 没有设备节点, 因此 ``register_chrdev()`` 直接以名字登记, 设备表
挂载为 /dev, 程序以 ``open("/dev/ttyACM0")`` 打开设备 (提交 58be49d 之后).
驱动在 ``sched_start()`` 之前登记, 设备表因此不需要锁. 目前登记的只有
ttyACM0.


终端行规程
==========

终端程序把每个按键单独发出, 自身不显示输入. 回显输入、处理退格、把回车
整理为一行, 这些处理若写在读取终端的程序中, 每个程序都要各写一遍. Linux
把这部分放在 tty 层的**行规程** (line discipline) n_tty 中, 读取终端的程序
在规范模式下只得到完整的行.

drivers/tty.c 实现其中命令行所需的部分 (提交 62a11c0), 对应 termios 的
四个标志:

- ICANON: 读者每次得到一整行, 以 ``\n`` 结尾.
- ECHO: 收到的字符立即发回终端. 退格与 DEL 删去前一个字符, 回显为
  ``\b \b``, 即退一格、以空格覆盖、再退一格.
- ICRNL: 回车 (CR) 作为换行. 终端发送 CR、LF 或 CR LF 都只结束一行.
- ONLCR: 输出中的 ``\n`` 改为 CR LF 发出, 否则终端的光标不会回到行首.

Leonix 没有信号机制, Ctrl-C 只丢弃当前行, 读者得到一个空行. 一行最长 31
个字符, 超出的输入被忽略.

终端层位于设备与驱动之间: USB 驱动把原始的读写函数交给 ``tty_register()``,
终端层再以 ttyACM0 的名字登记自己的读写函数.


USB 串口的接收
==============

提交 a2f1295 起, 主机写入的数据一律被丢弃. 提交 5725704 加入接收:
``usb_task()`` 把端点 2 中的字节移入 32 字节的环形缓冲区, 读者从缓冲区
取出.

缓冲区放不下时, 剩余的数据留在 USB 控制器的 bank 中, 该端点的中断保持屏蔽.
bank 未被释放, 控制器对主机后续的 OUT 包回答 NAK, 主机暂停发送. 读者取走
数据之后通知 ``usb_task()`` 继续接收. 数据因此不会丢失, 这一机制即 USB 的
流量控制.

发送同样经过 64 字节的环形缓冲区. 端点寄存器经 UENUM 选择, 该选择是全体
共用的一个寄存器, 两个任务交替选择不同的端点会互相干扰. 因此只有
``usb_task()`` 访问端点, shell 只读写缓冲区. 两个缓冲区各只有一个写入者与
一个读取者, 下标是 8 位的, 读写各为一条指令, 不需要加锁.

端口关闭期间, 发送缓冲区中的数据保留. shell 在开机时写出的提示符因此在终端
打开之后才发出, 排在回放的日志之后. 发送缓冲区写满时, 写入者等待下一次
打开.

每个包最多 63 字节, 比端点的包长少 1. 按 USB 2.0 5.8.3 节, 长度等于包长的
包不结束一次 bulk 传输, 主机可能等待后续的包; 短包使主机立即把数据交给
终端程序.


shell
=====

提交 b916273 加入的 shell 是 C 写的内核任务, 命令最初是其中的函数. 提交
be1f5ed 把命令移到 /bin, 但仍是内核中的 C 函数, 与内核共享全部内存与
硬件. 提交 392ed96 起, shell 也改为用户程序 /bin/sh, 由内核中的虚拟机
执行, 内核开机后只运行 /bin/sh; C 写的 shell 随之删除. 虚拟机、sh 与各程序见
vm.rst.

sh 只经由系统调用工作, 与用户程序在 Linux 中所处的边界相同. 这一边界由
解释器在每次访存与每个系统调用时检查, 程序无法越过.


栈与存储
========

以下是 C 写的 shell 时期的数字. shell 任务的栈为 256 字节, 任务表随之由 4
项增为 5 项. 按 avr-gcc 9.5.0 的
``-fstack-usage``, 最深的路径是格式化一行输出: ``shell_task()`` 67、
``sh_printf_P()`` 44、``vsnprintk_P()`` 22、``put_number()`` 34 与
``put()`` 2 字节, 合计 169 字节, 加上切换的 55 字节与金丝雀的 2 字节为
226 字节. 2026-10-10 在板子上执行各命令之后读到的最低余量为 28 字节, 即
实际用量 226 字节, 与推算相同.

加入 shell 之后, 映像的 text 为 11646 字节, ``__bss_end`` 为 0x06ea, 距
boot key 所在的 0x0800 还有 278 字节. 文件系统因此先要腾出 SRAM, 见 vfs.rst.
程序在 shell 的栈上运行之后, 该栈增为 288 字节; 改为 init 任务运行 /bin/sh
之后为 318 字节, 见 vm.rst.


实测
====

2026-10-10 用一个 Python 脚本经 /dev/cu.usbmodem101 逐条发送命令, 记录
板子的回复:

- ``help``、``ps``、``dmesg``、``uptime`` 与 ``devices`` 的输出正确.
  ``devices`` 后来由 ``ls /dev`` 取代.
- ``pss`` 加 DEL 再回车, 回显为 ``pss\b \b``, 执行的是 ``ps``.
- ``foo`` 回答 ``foo: not found``.
- ``abc`` 加 Ctrl-C, 回显 ``^C``, 该行被丢弃.
- 开机后第一次打开端口, 日志回放之后出现提示符.


尚未解决的问题
==============

- 只有一个终端. 液晶屏尚未登记为字符设备.
- 日志与 shell 的输出共用一个端口, 日志可能插在提示符与输入之间.
- 一行超过 31 个字符时多出的输入被静默忽略.
- 用户空间由软件隔离, 限制见 vm.rst 的"尚未解决的问题"一节.
