====================
格式化输出与内核日志
====================

**printk** 是 Linux 内核向内核日志写入一条消息的函数, 用法与 C 标准库的
printf 相近. Leonix 的 ``printk()`` 把消息格式化之后, 连同开机以来的秒数存入
SRAM 中的一个环形缓冲区, 再经 USB 串口送到电脑 (见 usb.rst). 格式化由
``snprintk()`` 完成, 液晶屏的显示与 ``panic()`` 也使用该函数. 代码在
lib/vsprintf.c 与 kernel/printk.c.


格式化函数
==========

``snprintk()`` 之前, 液晶屏上的每个数字由 ``lcd_put_right()`` 逐位拼接,
``panic()`` 的显示另有一套拼接代码. 内核日志需要第三套, 通用的格式化函数
因此被提前写出 (提交 4a10c16).

avr-libc 提供 ``vfprintf()``, 该函数支持浮点数与大量格式, 引入后映像会增加
一大段外部代码. lib/vsprintf.c 只实现 Leonix 用到的格式, 用 avr-gcc 9.5.0
``-Os`` 编译为 972 字节. 支持的转换为 ``%c``、``%s``、``%S``、``%d``、``%u``、
``%x`` 与 ``%%``, 宽度前可加 ``0`` (以零补齐) 或 ``-`` (左对齐), 宽度可写作
``*`` 由参数给出, ``l`` 表示 32 位参数. avr-gcc 的 int 是 16 位, 计时用的
jiffies 是 32 位, 因此 ``l`` 是必需的.

输出在 ``size - 1`` 个字符处截断, 结尾总有一个 ``'\0'``. 无法识别的转换按
原样复制, 例如 ``%q`` 输出为 ``%q``; 格式串末尾单独的 ``%`` 输出为 ``%``.
这两种写法的行为最初未定义, 主机测试发现之后才补充了处理.

``%*`` 与 ``%-`` 各自由一处显示的需要引入. 栈页把 16 列按任务数平分, 每列的
宽度在运行时才知道, 因此需要 ``%*`` (提交 6e12270). 日志页把记录的文字写在
左侧, 不足 16 列的部分须以空格补到行尾, 否则上一条较长记录的尾部会留在屏幕
上, 因此需要 ``%-`` (提交 c4205aa). 两者的写法与 C 标准及 Linux 的
``vsnprintf()`` 相同.


格式串放在 Flash 中
-------------------

AVR 的 Flash 与 SRAM 是两个独立的地址空间. C 代码中带初值的字符串属于 .data
段, 启动时被逐字节复制到 SRAM, 详见 avr.rst. 每个格式串因此会同时占用 Flash
与 SRAM, 而 SRAM 只有 2.5 KiB.

``snprintk()`` 与 ``printk()`` 都是宏, 把字面量格式串包进 avr-libc 的
``PSTR()``, 字符串于是只留在 Flash 中, 格式化函数用 ``pgm_read_byte()``
逐字节读取. 参数中的字符串同样可以放在 Flash 中, 以 ``%S`` 转换, ``panic()``
的原因名称即采用这种写法. 显示代码改用 ``snprintk()`` 之后 (提交 96855c0),
映像的 data 由 72 字节降为 4 字节.


主机测试
--------

lib/ 中的代码不依赖 AVR 的寄存器, 可以在开发机上编译与运行. 主机编译时
include/leonix/kernel.h 把 ``PSTR()`` 定义为原样返回, 把 ``pgm_read_byte()``
定义为普通的内存读取. ``make check`` 以主机的 C 编译器编译
tests/test_vsprintf.c, 逐条比较格式化的结果与预期的字符串. 格式化的错误
因此不必烧录到板子上才能发现, 上文两种未定义的写法即在这一测试中发现.


内核日志
========

``printk()`` 格式化一条消息, 记下 ``get_jiffies() / HZ`` 即开机以来的秒数,
再把这条记录写入缓冲区 ``log_buf`` (提交 4945756). 缓冲区写满之后, 新记录
覆盖最旧的一条. 名称与做法沿用 Linux 的 log_buf.

记录是定长的: 2 字节的秒数与 14 字节的文字, 文字最多 13 个字符. 变长记录
可以容纳更多消息, 但需要额外的长度字段与回绕处理. 13 个字符的上限来自
液晶屏, 日志页的第 1 行只有 16 列; 日志页后来被删除, 该上限保留至今.

缓冲区最初保留 4 条, 合计 64 字节. 4 条记录在开机第 1 秒就被写满, 终端稍晚
打开时, 开机记录已被覆盖. 液晶屏不再显示日志之后, 缓冲区扩大到 16 条, 合计
256 字节 (提交 ec76b10).

格式化在调用者的栈上进行, 只有写入缓冲区的几条赋值在关闭中断的情况下
执行. 任务、中断处理程序与 ``sched_start()`` 之前的代码都可以调用
``printk()``, 写入的记录不会被另一次写入从中间截断. ``log_read()`` 以同样的
方式按序号复制出一条记录, 序号从 1 起, 即开机以来写入的第几条.

目前写入日志的事件为: 开机, 液晶屏背板的 I2C 地址, 液晶屏离线、恢复与
快速拔插后的重新初始化, USB 配置完成, 以及各任务的栈余量创出新低. 这些事件此前只改变屏幕上的显示, 屏幕恢复之后,
发生过几次、在什么时刻发生都无从得知.


日志页
======

日志页存在于提交 0e10af2 至 dd8439f 之间, USB 串口可用之后被删除. 下文
记录该页的设计与当时观察到的问题.

液晶屏每 5 秒换一页, 依次为状态页、栈页与日志页 (提交 0e10af2). 日志页第 0
行是 "log", 最新一条记录的序号与秒数, 序号左对齐, 秒数右对齐; 第 1 行是该条
的文字, 以空格补足 16 列.

2026-10-10 在板子上烧录该映像, 日志页上未出现 "Leonix booted".
该条是序号 1 的记录, 在 ``main()`` 中写入; 液晶屏任务找到背板之后紧接着写入
序号 2 的地址记录. 日志页只显示最新的一条, 第一次显示日志页时, 最新的一条
已是序号 2. 序号 1 仍在缓冲区中, 只是无从显示. 这一观察是加入 USB 串口的
直接原因.


栈的代价
========

``printk()`` 本身的栈帧为 24 字节, 其中 16 字节是记录. 加上
``vsnprintk_P()`` 22 字节、``put_number()`` 34 字节与 ``put()`` 2 字节, 一次
调用在调用者之下最多用 82 字节. Leonix 的任务栈按实测用量确定 (见 scheduler.rst
的"栈的实测"一节), 多出 82 字节的调用链可能超出液晶屏任务 224 字节的栈.

推算方法与 scheduler.rst 的"栈的预算"一节相同: ``-fstack-usage`` 给出每个
函数的栈帧, 其中已含返回地址; 沿最深的调用链逐项相加, 再加上切换本身的 55
字节与金丝雀的 2 字节. 提交 96855c0 用这一方法推算液晶屏任务用量为 172 字节,
板上读到的也是 172 字节, 该方法由此得到确认.

最初的写法在驱动 drivers/lcd.c 的 ``pcf_probe()`` 中调用 ``printk()``, 记录
找到的地址. 该位置处于 ``lcd_task()``、``lcd_show_banner()``、``lcd_init()``
之下, 当时推算的最深路径约 260 字节, 超过 224 字节的栈. 该推算的逐项
数值没有保留. 记录随后移至 ``lcd_task()``: 驱动只通过 ``lcd_address()`` 提供地址, 由任务在初始化成功之后
写入日志. 驱动处于各条 I2C 调用链的中段, 在驱动中调用 ``printk()``, 其 82 字节
会叠加在整条调用链上.

显示函数是否内联, 在这一过程中先后作出了相反的选择. 提交 96855c0 中三个
显示函数被内联进 ``lcd_task()``, 各自的行缓冲区同时占用该任务的栈帧, 帧由
30 字节增至 84 字节; 栈页的标签改由 ``lcd_puts_P()`` 直接从 Flash 写出之后,
帧降为 60 字节. 当时也比较过以 ``noinline`` 禁止内联, Flash 多 142 字节,
最深路径反而更深, 该做法因此落选. 加入 ``printk()`` 之后, ``lcd_task()``
自身的调用链也要经过一次格式化, 内联进来的缓冲区会叠加在每次 ``printk()``
与 I2C 传输之下. 提交 0e10af2 因而把四个显示函数都改为 ``noinline``,
``lcd_task()`` 的帧降为 34 字节, 各缓冲区只在对应的显示函数运行时存在.
内联与否的得失取决于最深路径经过哪些函数, 调用图变化之后需要重新比较.

按 avr-gcc 9.5.0 的 ``-fstack-usage``, 现在最深的路径是日志页的格式化:
``lcd_task()`` 34、``lcd_show_log()`` 49、``snprintk_P()`` 4、
``vsnprintk_P()`` 22、``put_number()`` 34 与 ``put()`` 2 字节, 合计 145 字节,
加上切换的 55 字节约为 200 字节. 224 字节的栈减去金丝雀之后余量约 22 字节.

2026-10-10 在板子上读到提交 0e10af2 的映像的余量为 31、31、51、13 字节.
液晶屏任务的实际用量为 171 字节, 比推算少 29 字节, 与 96855c0 的 172 字节
相差 1 字节. 推算的最深路径要求节拍中断恰好在日志页格式化数字时到来, 而
该格式化每 15 秒中只在日志页的 5 秒内发生, 每次只持续很短的时间. 运行期间
这一路径大概率没有被执行; 这是依据推算作出的判断, 该路径的实际深度没有
测得. 200 字节因此仍作为该栈的预算依据.

提交 dd8439f 删除栈页与日志页之后, 液晶屏任务的最深路径不再经过日志页的
格式化, 推算降为约 192 字节. 同日读到的最低余量为 39 字节, 即实际用量 183
字节.


栈余量的报告
============

栈页删除之后, 各任务的余量改由 ``printk()`` 报告 (提交 dd8439f). 液晶屏任务
每秒调用一次 ``report_stack_usage()``, 某个任务的余量低于此前的最低值时,
写一条 ``stack t2 39`` 形式的记录, 空闲任务写作 ``stack idle 13``. 做法与
Linux 的 ``CONFIG_DEBUG_STACK_USAGE`` 相同: 只报告新低, 开机几秒之后出现的
报告就说明某条更深的路径刚刚运行过. 液晶屏离线时, 该检查在每次重试时进行,
离线期间的新低同样会被报告.

2026-10-10 开机十几秒后打开串口, 读到两个 LED 任务 31 字节、液晶屏任务
39 字节、USB 任务 45 字节、空闲任务 13 字节. 此后拔插液晶屏背板, USB 任务
降至 27 字节, 见 usb.rst 的"栈与存储"一节.


尚未解决的问题
==============

- 不接电脑时, 日志只能在下次打开串口时回放, 且只有最近 16 条.
- 中断处理程序调用 ``printk()`` 时, 格式化在被打断的任务的栈上进行, 最多 82
  字节的用量不在 TASK_STACK_RESERVE 之内. 目前没有中断处理程序调用
  ``printk()``; 一旦有, TASK_STACK_RESERVE 需要相应增加.
- 消息超过 13 个字符即被截断, 没有标记提示截断的发生.
