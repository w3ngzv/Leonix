====================
USB 虚拟串口与控制台
====================

**CDC-ACM** (Communications Device Class, Abstract Control Model) 是 USB
规范中模拟串口的设备类. 符合该类的设备接到电脑上, 操作系统用自带的驱动把
该设备呈现为一个串口, macOS 上为 /dev/cu.usbmodem*, Linux 上为
/dev/ttyACM*. Leonix 用 ATmega32U4 自带的 USB 控制器实现了一个最小的
CDC-ACM 设备, 用于两件事: 把内核日志送到电脑, 以及在烧录前让板子自行进入
bootloader. 代码在 arch/avr/usb.c.


USB 的基本概念
==============

USB 总线上的一切传输都由主机 (电脑) 发起. 设备从不主动发送, 只在主机询问
时回答: 主机发出 IN 令牌, 设备才送出数据; 主机发出 OUT 令牌并附上数据,
设备收下. 设备没有准备好时回答 NAK, 主机随后重试.

设备内部的收发单位是**端点** (endpoint), 编号 0 至 15, 每个端点有方向与
类型. 端点 0 是控制端点, 每个设备都有, 主机通过该端点识别与配置设备. 其余
端点由设备自行声明. ATmega32U4 的端点 0 至 6 各有一块缓冲区, 位于 USB
控制器专用的 832 字节 DPRAM 中, 不占用 SRAM (数据手册 22.1 节).

控制传输分为三个阶段 (USB 2.0 5.5 节):

1. SETUP 阶段: 主机发出 8 字节的请求, 例如读取设备描述符.
2. 数据阶段: 按请求的方向, 由设备发送或由主机发送若干字节. 不带数据的请求
   没有这一阶段.
3. 状态阶段: 与数据方向相反的一个空包, 表示整个请求完成.

设备不支持某个请求时, 以 STALL 回答, 即 USB 2.0 9.2.7 节所说的请求错误.


枚举
====

设备插入之后, 主机依次完成下列步骤, 这一过程称为**枚举**
(enumeration):

1. 主机复位总线. 设备此时只响应地址 0.
2. 主机读取**设备描述符** (device descriptor): USB 版本、设备类、端点 0
   的包长、厂商号 (VID) 与产品号 (PID).
3. 主机以 SET_ADDRESS 给设备分配一个地址, 此后设备只响应该地址.
4. 主机读取**配置描述符** (configuration descriptor), 其中依次排列着各
   接口与各端点的描述符.
5. 主机以 SET_CONFIGURATION 选定配置. 设备此时才建立端点 0 以外的端点.

请求码与描述符类型的取值见 USB 2.0 表 9-4 与表 9-5. 设备描述符中的 bcdUSB
为 0x0200, 主机因此还会询问 DEVICE_QUALIFIER 描述符, 该描述符只有支持高速
的设备才有. USB 2.0 9.6.2 节规定, 只支持全速的设备收到该请求时必须回答请求
错误, Leonix 以 STALL 回答.

SET_ADDRESS 的处理顺序由数据手册 22.7 节规定: 先把地址写入 UADD, 送出状态
阶段的空包, 之后才置位 ADDEN. 若立即启用新地址, 状态阶段的空包将以新地址
发出, 而主机此时仍在询问地址 0.


CDC-ACM 的描述符
================

一个 CDC-ACM 设备由两个接口组成 (CDC 1.2 与 PSTN 1.2):

- 通信接口, 类代码 0x02, 子类 0x02 (抽象控制模型). 该接口带一个中断 IN
  端点, 用于向主机报告串口线路状态的变化. Leonix 没有这类变化要报告,
  端点 1 声明之后从不发送, 但规范要求该端点存在.
- 数据接口, 类代码 0x0A. 端点 2 (bulk OUT) 接收主机写入的数据, 端点 3
  (bulk IN) 向主机发送数据.

通信接口之后跟着四个功能描述符, 类型均为 CS_INTERFACE (0x24): header 声明
所依据的 CDC 版本; call management 说明设备不自行处理呼叫; ACM 描述符的
bmCapabilities 取 0x02, 即支持 SET_LINE_CODING、GET_LINE_CODING 与
SET_CONTROL_LINE_STATE (PSTN 1.2 表 4); union 描述符声明两个接口属于同一
功能, 其中通信接口为控制接口.
配置描述符连同这些内容共 67 字节, 全部放在 Flash 中.

VID 与 PID 沿用 Arduino 给运行中的 Leonardo 应用分配的 0x2341 与 0x8036.
Caterina 用的是 0x0036, 主机凭 PID 区分应用与 bootloader. 这一对编号属于
Arduino, 只适合个人使用.

上述描述符与请求码的取值, 在代码写成并在板子上枚举成功之后, 于 2026-10-10
逐项对照了 USB 2.0、CDC 1.2 与 PSTN 1.2 的原文, 未发现不符之处. 各文件的
来源见 references/index.rst.


时钟
====

全速 USB 的数据率是 12 Mbit/s, USB 控制器需要 48 MHz 的时钟, 由片内的 PLL
从 16 MHz 晶振倍频得到 (数据手册 6.11.5 与 6.11.6 节):

- PLLCSR 的 PINDIV 置位, 先把 16 MHz 二分频为 PLL 要求的 8 MHz 输入.
- PLLFRQ 的 PDIV 取 0100, PLL 输出 48 MHz; PLLUSB 为 0, 输出不再分频,
  直接送给 USB 控制器.

数据手册 6.11.5 节称 PLL 锁定需要数毫秒. ``usb_init()`` 最多等待 10 毫秒, 仍未锁定即关闭
USB 控制器并返回失败, 液晶屏与其余任务照常运行. 全速 USB 只能使用外部晶振
(数据手册 21.4 节), Leonardo 的 16 MHz 晶振满足这一条件.

控制器的上电顺序取自数据手册 21.12 节: 打开 USB 稳压器 (UVREGE), 打开
控制器并保持时钟冻结, 启动 PLL 并等待锁定, 解冻时钟并打开 VBUS 检测
(OTGPADE), 最后清除 DETACH. 清除 DETACH 之后, 只要 VBUS 存在, 控制器就把
D+ 上拉, 主机据此发现设备 (数据手册 22.2 节).


中断与任务的分工
================

USB 控制器有两个中断向量: 通用中断 (向量 10) 报告总线复位等事件, 端点中断
(向量 11) 报告某个端点收到了 SETUP 或数据.

控制请求的第一版写在端点中断之内, 该版本没有烧录. 一个控制传输由多个包
组成, 包与包之间要等待主机的下一个令牌, 每次最长 10 毫秒. 在中断中等待,
这段时间内中断一直关闭, 节拍随之丢失.

栈是该写法的另一个缺陷. 中断处理程序运行在被打断的任务的栈上, 按 avr-gcc 9.5.0 的 ``-fstack-usage``, 端点中断 28
字节、``ep0_send()`` 11 字节、``ep_wait()`` 2 字节, 加上中断压入的 PC 共
43 字节, 空闲任务的栈只余 13 字节 (见 scheduler.rst 的"栈的实测"一节).

最终的写法与 I2C 相同 (见 lcd.rst 的"中断驱动的传输"一节): 端点中断只屏蔽
引发中断的端点, 记下事件, 再唤醒 ``usb_task()``; 请求由该任务处理, 处理完
之后重新打开该端点的中断. 两个向量写在 switch.S 中, 与节拍中断及 TWI 中断
使用同一种寄存器帧. 中断处理函数连同 ``wake_up()`` 只用 4 字节, 比
``schedule()`` 的 20 字节浅, 栈的用量因此包含在 TASK_STACK_RESERVE 之内.

ATmega32U4 的各端点共用一组寄存器: 先把端点号写入 UENUM, UEINTX、UEDATX
等寄存器才指向该端点 (数据手册 22.5 节). 中断可能在 ``usb_task()`` 选定某个
端点之后到来, 中断处理函数因此先保存 UENUM, 返回前再写回.

总线复位之后, 端点 0 以外的端点全部失效 (数据手册 22.4 节). 通用中断在
复位结束时重新配置端点 0, 这一操作只有几次寄存器写入, 在中断中完成.


控制台
======

``printk()`` 不直接调用 USB 驱动. 驱动在 ``usb_init()`` 中以
``register_console()`` 注册一个通知函数, ``printk()`` 每写入一条记录就调用
该函数一次, 该函数只唤醒 ``usb_task()``. 写法沿用 Linux 的控制台注册.
``printk()`` 可能在中断中调用, 而发送要等待端点, 只能在任务中进行.

``usb_task()`` 被唤醒后, 用 ``log_read()`` 逐条取出尚未发送的记录, 格式化
为 ``[秒数] 文字`` 加回车换行, 每行作为一个包从端点 3 发出.

记录只在主机置位 DTR 时发送. DTR 是 SET_CONTROL_LINE_STATE 请求中的最低位
(PSTN 1.2 表 18), 终端程序打开串口时置位, 关闭时清除. 端口无人读取时,
端点 3 的两个缓冲区很快写满, 之后每发一行都要等满 10 毫秒的超时, 以 DTR
为条件可以避免这一开销.

DTR 由 0 变 1 时, 先回放缓冲区中仍保留的记录. 开机记录在终端打开之前就已
写入, 不回放就无从看到. 缓冲区只保留最近 16 条, 已被覆盖的记录以
``(N lost)`` 一行注明条数.

主机在端口打开期间停止读取时, 发送等满超时之后放弃剩余的记录, 不再重试.
重试会使 ``usb_task()`` 在无人读取的端口上反复等待.


免按复位键烧录
==============

Caterina 在看门狗复位之后检查 SRAM 地址 0x0800 处的字, 该字为 0x7777 时
留在 bootloader 中等待编程器 (见 booting.rst 第 3 节). Arduino core 的做法
是: 主机以 1200 波特率打开 CDC 端口再关闭, 应用收到之后写入该值, 并让看门狗
复位芯片. Leonix 沿用同一约定, 主机一侧因此可以使用现成的工具.

SET_LINE_CODING 请求携带主机设定的波特率 (PSTN 1.2 表 17). USB 虚拟串口
的传输速率与该值无关, 1200 在这里只作为约定的信号. 收到
SET_CONTROL_LINE_STATE 时, 若当前波特率为 1200 且 DTR 已清除, 驱动写入
boot key, 再以 120 毫秒的超时打开看门狗. 120 毫秒足以让状态阶段的空包
送出, 主机随后看到设备离开总线.

0x0800 位于启动栈中. ``sched_start()`` 之后启动栈只在 ``panic()`` 中使用,
写入 boot key 不会破坏正在使用的数据. 但 .data 与 .bss 一旦增长到 0x0800,
boot key 就会改写变量, 因此 Makefile 在每次链接后检查 ``__bss_end``, 超过
该地址即删除映像并报错.

``make flash`` 先以 1200 波特率打开并关闭端口, 等待该端口消失, 再等待
bootloader 的端口出现, 然后运行 avrdude. 端口在 1 秒内没有消失时, 认为板子
已在 bootloader 中, 例如刚按过复位键, 直接运行 avrdude. 板上的固件没有这一
功能时, 按复位键的旧做法因此仍然可用.


栈与存储
========

``usb_task()`` 的栈为 224 字节. 按 avr-gcc 9.5.0 的 ``-fstack-usage``, 最深
的路径是 ``console_flush()`` 格式化数字: ``usb_task()`` 16、
``console_flush()`` 66、``snprintk_P()`` 4、``vsnprintk_P()`` 22、
``put_number()`` 34 与 ``put()`` 2 字节, 合计 144 字节, 加上切换的 55 字节
与金丝雀的 2 字节为 201 字节. ``console_flush()`` 以 noinline 留在
``usb_task()`` 之外, 其行缓冲区与记录因此不会叠加在处理请求时调用的
``printk()`` 之下.

2026-10-10 在板子上读到该栈的最低余量为 27 字节, 即实际用量 195 字节,
出现在拔插液晶屏背板、串口正在发送日志的时候, 比推算少 6 字节.

映像的 text 在枚举完成时由 7858 字节增为 9432 字节, 加入控制台之后为
10170 字节, 加入 bootloader 入口之后为 10248 字节.


实测
====

2026-10-10 在 macOS 上:

- 烧录枚举部分之后, ``ioreg -p IOUSB`` 列出名为 Leonix 的设备, 地址 2,
  并出现 /dev/cu.usbmodem101. 打开该端口并写入 200 字节之后设备仍在.
- 加入控制台之后, ``cat /dev/cu.usbmodem101`` 回放了开机的三条记录. 拔插
  液晶屏背板产生的三条记录随即出现.
- 加入 bootloader 入口之后, Leonix 运行时执行 ``make flash``, 未按复位键
  即完成烧录.


尚未解决的问题
==============

- 由圆口插座或 VIN 独立供电、不接 USB 线的情形尚未测试. 此时 VBUS 不存在,
  按数据手册 22.2 节控制器不会连接到总线, ``usb_task()`` 应当一直睡眠.
- 运行中拔下 USB 线再插回的情形尚未测试. 插回时主机复位总线,
  端点 0 被重新配置, 枚举预期可以重新完成.
- 总线挂起 (suspend) 没有处理. 电脑睡眠时 USB 控制器不会进入低功耗状态.
- 主机写入的数据被丢弃. 由电脑设定时间等功能需要先实现接收.
- ``ep_wait()`` 在任务中忙等主机的令牌, 等待期间该任务占用 CPU. 对空闲
  比例的影响尚未测量.
- 设备描述符没有序列号字符串. 同一台电脑接两块 Leonix 时, 两者无法稳定地
  区分.
