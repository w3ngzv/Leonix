==========================
VFS、文件系统与 /bin
==========================

**VFS** (Virtual File System) 是 Linux 内核中把各种文件系统与设备并入同一个
路径命名空间的一层. 程序只调用 ``open()``、``read()``、``write()`` 与
``close()``, 不必知道文件位于哪个文件系统, 也不必知道对面是文件还是设备,
这一设计常被概括为"一切皆文件". Leonix 实现了这一层的最小形式: 设备挂载在
/dev, 程序挂载在 /bin, 内核状态挂载在 /proc, 其余路径属于 EEPROM 上的文件
系统 lxfs. 代码在 fs/ 与 drivers/eeprom.c.


使用
====

在 shell 中::

  # ls /
  bin
  dev
  notes
  # ls /bin
  cat
  df
  ...
  # echo hello > notes
  # echo more >> notes
  # cat notes
  hello
  more
  # rm notes
  # df
  736 bytes free

``ls /bin`` 列出的每个名字都是一个程序, 以名字执行. 不以 / 开头的路径从根
目录算起, 根目录是唯一的当前目录. 错误以 Linux 的错误码报告, 例如
``error 2`` 是 ENOENT, ``error 30`` 是 EROFS.


腾出 SRAM
=========

提交 4c97012 时, .data 与 .bss 已到 0x06ea, 离 0x0800 处 Caterina 的 boot
key 只剩 278 字节, 放不下文件描述符表与文件系统的缓冲区 (boot key 见
booting.rst 第 3 节). boot key 之上的 766 字节原是 ``main()`` 与 ``panic()``
的启动栈, ``sched_start()`` 之后大部分时间闲置.

提交 b400b45 把液晶屏、USB 与 shell 三个任务的栈移到 boot key 之上:

  ===============  ========================================
  地址             内容
  ===============  ========================================
  0x0100 起        .data, 之后是 .bss
  至 0x07ff        启动栈, 自 0x07ff 向下
  0x0800 - 0x0801  boot key
  0x0802 起        .noinit: 液晶屏、USB 与 init 的任务栈
  ===============  ========================================

三块栈以 ``section(".noinit.stacks")`` 声明, 链接时以
``--section-start=.noinit=0x800802`` 放到 0x0802. avr-gcc 给 .noinit 段的只有
ALLOC 标志, 该段不占 Flash, 启动代码也不清零; ``task_create()`` 本来就会把
整块栈填满 0xa5. 链接器给数据地址加 0x800000 的偏移, 0x800802 即 SRAM 的
0x0802.

启动栈原先从 RAMEND (0x0aff) 向下. 任务栈搬到上方之后, ``main()`` 的栈与
这些任务栈重叠, ``task_create()`` 填充 0xa5 时会改写 ``main()`` 自己的栈. 复位与
``panic()`` 因此都把 SP 设为 0x07ff. 布局写在 include/leonix/memlayout.h.

按 ``-fstack-usage``, ``main()`` 经 ``printk()`` 约用 86 字节, ``panic()``
经格式化约用 90 字节. Makefile 在每次链接后检查两条边界: .bss 末尾与 boot
key 之间至少留 128 字节, .noinit 不越过 SRAM 末尾. 两条检查都以故意改小的
限值试过, 越界时删除映像并报错.

2026-10-11 在板子上, 各任务的栈余量与搬迁前相同, 未按复位键的 make flash
再次成功, 说明 boot key 未被改写. ``panic()`` 在新栈上的运行尚未在板上
触发验证.


struct file 与文件描述符
========================

提交 84e0b53 的字符设备只能按名字取得一组读写函数. 提交 58be49d 加入 Linux
的写法: ``open()`` 返回一个**文件描述符** (file descriptor), 即 ``files[]``
表中的下标; 表项 ``struct file`` 记下该文件的 ``file_operations``、读写位置
与打开标志. ``read()`` 与 ``write()`` 经由文件描述符找到 ``struct file``,
再调用其中的函数.

``open()`` 的标志与错误码都取 Linux 的数值, 只有 ``O_DIRECTORY`` 例外:
Linux 的值 0x10000 放不进这里 16 位的标志, 取 0x8000.

没有进程, 描述符表只有一张, 共 4 项, 属于 shell 与 shell 运行的程序. shell 开机
时以 /dev/ttyACM0 打开 0 号描述符, 再以 ``dup2()`` 复制为 1 号, 即标准输入
与标准输出. 与 Linux 不同, ``dup2()`` 复制出的两个描述符各有自己的读写
位置, 同一个文件只应经由其中一个读写.


挂载与路径
==========

文件系统之内没有子目录, 路径的解析只按挂载点分派:

  =======  =========================  ============================
  挂载点   文件系统                   代码
  =======  =========================  ============================
  /bin     romfs, Flash 中的程序      fs/romfs.c, tools/mkromfs.py
  /dev     字符设备                   fs/char_dev.c
  /proc    内核状态的文本             fs/procfs.c
  /        lxfs, EEPROM               fs/lxfs.c, drivers/eeprom.c
  =======  =========================  ============================

``open()`` 依次比较挂载点, 路径以挂载点开头、且其后是 ``/`` 或字符串末尾时
即交给该文件系统, 剩余部分作为文件系统内的路径. / 排在最后, 接住其余路径.
``ls /`` 先列出其他挂载点, 再列出 lxfs 的文件, 与 Linux 中 /dev 是根文件
系统里一个目录时的结果相同.

Leonix 没有 ``chdir()``, 不以 / 开头的路径由 VFS 在前面补上 / (提交
82dd246). 在 Linux 中 ``echo hi > notes`` 写到当前目录, 这里写到根目录.


lxfs
====

lxfs 是 Leonix 的根文件系统, 位于芯片自带的 1 KiB EEPROM 上, 只有一个目录
(提交 8115ae2). EEPROM 被分为 32 块, 每块 32 字节:

  ======  ==================================================
  偏移    内容
  ======  ==================================================
  0       超级块: 魔数 "LXFS", 版本号
  8       分配表: 每块一个字节
  40      目录: 16 项, 每项为文件名 12 字节、首块号与长度
  288     数据: 第 9 至 31 块, 共 736 字节
  ======  ==================================================

分配表的写法取自 FAT: 每块对应一个字节, 记下同一文件的下一块的块号, 或者
记为空闲 (0xff) 与链尾 (0xfe). 文件的各块因此不必连续, 删除文件只需把链上
各块标为空闲, 不必搬动数据.

空闲标记取 0xff, 即空白 EEPROM 的内容. 首次开机时没有魔数, lxfs 自行格式化,
而分配表与目录本来就是 0xff, 实际写入的只有超级块的 5 个字节, 并记一条
``mkfs lxfs`` 日志.

文件只能在末尾写入: 以 ``O_APPEND`` 打开, 以 ``O_TRUNC`` 清空后写入, 或者
文件为空. 在中间写入返回 EINVAL. shell 的 ``>`` 与 ``>>`` 正对应前两种.
写入时先写数据, 再写覆盖这些数据的长度. 写到一半复位时, 文件保持原样,
至多留下一个已分配而无人引用的块. lxfs 没有找回这种块的检查程序.

元数据的大小与最初的估计不同. 目录 16 项、每项 15 字节就占 240 字节, 连同
超级块与分配表共 288 字节, 即 9 块. 最初按 3 块估计, 数据区因此由 928 字节
降为 736 字节.

EEPROM 与寿命
-------------

EEPROM 的读写交给 avr-libc 的 ``eeprom_read_block()`` 与
``eeprom_update_block()`` (drivers/eeprom.c). 后者先读出原值, 只写入发生
变化的字节. 每写入一个字节需要 3.3 毫秒 (数据手册表 5-3). avr-libc 2.0 的
反汇编显示, 等待期间中断的状态保持调用者的设置, 只有 EEMPE 与 EEPE 两次
定时写入时关闭中断, 其余任务因此照常运行.

数据手册 5.3 节给出 EEPROM 的寿命为至少 100,000 次擦写. lxfs 没有磨损
均衡, 写得最频繁的是分配表与目录项, 每次写文件都会改写. 按每天写 100 次
估计, 约 3 年达到寿命.

烧录不会清除 EEPROM. Caterina 的擦除命令只擦 Flash (Caterina.c 中处理
``'e'`` 命令的分支), make flash 又以 ``-D`` 跳过擦除. 高熔丝 0xd8 中 EESAVE
未编程, 经 ISP 编程器全片擦除时 EEPROM 会被清空, 该情形与 make flash 无关.

主机测试
--------

lxfs 不直接访问 EEPROM, 读写经由 ``lxfs_init()`` 传入的两个函数. tests/
test_lxfs.c 以一块初值为 0xff 的 1 KiB 数组代替 EEPROM, 在开发机上测试
格式化、跨块写入、追加、截断、文件名过长、写满、目录满、删除与重新挂载,
并统计实际写入的字节数. ``make check`` 运行这一测试.


/bin
====

提交 be1f5ed 起, /bin 是一张编译进内核的 C 函数表, 由 binfs 挂载, 命令
仍是内核中的函数, 与内核共享全部内存与硬件. 提交 e31b377 把 /bin 换成
Flash 中的只读文件系统 romfs, 文件内容是虚拟机的程序, 函数表与 binfs 随之
删除. 程序、虚拟机与 exec() 见 vm.rst.

romfs 在内核编译时由 tools/mkromfs.py 生成: leonix-coreutils 编出的每个
程序成为一个 PROGMEM 数组, 连同文件名列在一张表中. 文件可以读出, 例如
``cat /bin/ls`` 读出的是 ls 的字节码, 也可以经 ``peek()`` 按偏移读取单个
字节, 虚拟机就是这样取指令的. 写入与创建返回 EROFS. 这一做法与 Linux 以
initramfs 带上最初的程序相同; 不同之处在于 romfs 位于 Flash 中, 运行期间
无法替换, 更换程序需要重新烧录.


实测
====

2026-10-11 用 .dev 中的串口脚本逐条发送命令:

- 首次开机自动格式化, 日志中出现 ``mkfs lxfs``, ``df`` 报告 736 字节.
- 写入、追加、读回正确; 删除之后再删除返回 ENOENT.
- ``cat /dev`` 返回 EISDIR, ``rm /dev/ttyACM0`` 与 ``echo x > /bin/new``
  返回 EROFS.
- 写入一个文件之后执行 make flash, 重启之后文件仍在, 内容不变.
- ``ls /bin`` 列出当时的 9 个 C 程序. ``cat`` 与 ``rm`` 接受多个参数, 遇到
  不存在的文件时报错并继续处理其余参数.
- ``ps > psout`` 把输出写入文件, ``cat psout`` 读出.
- 未知命令回答 ``not found``, 超过 6 个词回答 ``too many words``.

以上为提交 be1f5ed 时的结果, 当时映像的 text 为 17094 字节, ``__bss_end``
为 0x04be. 改为虚拟机程序之后的测试见 vm.rst.


尚未解决的问题
==============

- lxfs 只能在文件末尾写入, 没有子目录, 没有磨损均衡, 也没有检查程序找回
  写到一半时留下的块.
- 描述符表只有一张, 只有 init 任务, 即 sh 与 sh 运行的程序, 可以使用文件.
- /bin 中的程序无法在运行时增加, lxfs 中的程序可以, 但还没有从电脑写入
  程序文件的办法, 见 vm.rst.
- 管道 (``|``) 与标准错误输出尚未实现, 错误信息写在标准输出.
- ``panic()`` 在新启动栈上的运行尚未在板上验证.
