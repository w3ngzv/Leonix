================
虚拟机与用户空间
================

**用户空间** (user space) 是操作系统中运行普通程序的一侧, 程序在这里只能
经由**系统调用** (system call) 请求内核代为访问设备与内核数据. Linux 依靠
处理器的 MMU 与特权级把两侧隔开. ATmega32U4 两者都没有, 而且只能执行
Flash 中的指令. Leonix 因此以软件实现这一边界: 用户程序是一台虚拟机的
字节码, 由内核中的解释器执行. 内核只负责调度、驱动、文件系统与系统调用,
shell 与全部命令都是用户程序. 代码在 kernel/vm.c、kernel/exec.c 与
init/init.c, 程序与汇编器分别在另外两个仓库中.


三个仓库
========

  ===================  ===================================  =================
  仓库                 内容                                 在本仓库中的位置
  ===================  ===================================  =================
  Leonix               内核, 包括虚拟机的解释器             本仓库
  Leonix_toolchain     汇编器 lxasm.py                      external/toolchain
  Leonix_coreutils     sh、ls、cat 等程序的源码             external/coreutils
  ===================  ===================================  =================

划分沿用 Linux 的生态: 内核、binutils 与 GNU coreutils 是三个独立的项目.
汇编器是工具链, 不属于内核, 内核的 ``make check`` 与 coreutils 都以该汇编器
汇编程序. 程序的命令名与行为取自 GNU coreutils 与 procps, 没有使用其代码:
GNU 的 C 源码需要 C 库与远多于此的内存, 其许可证 GPLv3 也与本项目的
GPLv2 (仅限该版本) 不相容.

两个仓库以 git 子模块的形式检出在 external/ 下, 地址列在顶层的 .gitmodules
中, 各自固定在内核最后一次构建与测试时的提交上, external/README 说明拉取
的方法. 内核的 Makefile 以 TOOLCHAIN 与 COREUTILS 两个变量指向这两个目录.


隔离由什么保证
==============

虚拟机的地址空间分为两段: 0x8000 以下是代码, 只读; 0x8000 起是该程序的
数据内存, 可读写, 最多 160 字节. 解释器在每一次读写时检查地址是否落在这
两段之内, 向代码写入、越过数据内存末尾都会使程序因故障停止. 程序的指令
中没有访问 I/O 寄存器、关闭中断或跳出虚拟机的指令, 离开虚拟机的唯一途径
是 SYS 指令, 即系统调用. 系统调用的每个缓冲区参数, 内核同样先检查该缓冲区
是否落在该程序自己的内存之内.

这一隔离由解释器保证, 与 Linux 的 eBPF 相同, 都由软件强制. 差别在于 eBPF
在加载时由校验器证明程序安全, 再编译为原生代码运行; 这里在每条指令执行
时检查, 实现简单, 代价是速度.

解释器本身、驱动与内核仍是原生代码, 不受这一隔离保护.


指令集
======

虚拟机是 16 位的栈式机器, 与 Forth 相近: 指令从数据栈取操作数, 结果压回
数据栈; 返回地址在另一个返回栈上. 数据栈 16 项, 返回栈 8 项, 溢出与下溢
都是故障. 全部操作码定义在 include/leonix/vm.h:

  ======================  =============================================
  类别                    指令
  ======================  =============================================
  常数                    lit8, lit16
  栈                      dup, drop, swap, over, rot, pick
  算术与逻辑              add, sub, mul, divu, modu, and, or, xor,
                          shl, shr, not, neg, muldiv
  比较                    eq, lt (有符号), ult (无符号), eqz
  内存                    ldb, stb, ldw, stw
  控制                    jmp, jz, jnz, call, ret, >r, r>, r@
  系统调用                sys
  ======================  =============================================

``muldiv`` 计算 a * b / c, 乘积保留 32 位, 即 Forth 的 ``*/``. 16 位的数在
求比例时容易溢出: uptime 以百分之一秒计算空闲比例, idle * 100 在运行十分钟
后就超出 16 位 (提交 46848c2).

程序文件以 6 字节的头开始: 魔数 ``LX``、版本号、保留字节与数据内存的大小,
其后是代码. 版本号随指令集或系统调用编号的改变而增加, 内核拒绝运行其他
版本的程序.


系统调用
========

编号定义在 include/leonix/syscall.h. 参数按 C 原型的顺序压栈, 结果替换
参数; 出错时返回负的 errno, 与 Linux 系统调用在 libc 处理之前的约定相同.

  =========  ===================================  ===========================
  编号       调用                                 结果
  =========  ===================================  ===========================
  0          exit(status)                         不返回
  1          read(fd, buf, count)                 字节数
  2          write(fd, buf, count)                字节数
  3          open(path, flags)                    描述符
  4          close(fd)                            0
  5          readdir(fd, buf, size)               1, 末尾为 0
  6          unlink(path)                         0
  7          exec(argc, argv)                     程序的退出码
  8          dup2(oldfd, newfd)                   newfd
  9          statfs()                             / 上的空闲字节数
  =========  ===================================  ===========================

``write()`` 的缓冲区可以位于代码区: 程序中的字符串常量就在代码里, 内核以
16 字节为一段读出后写入.


exec 与程序的运行
=================

``exec()`` 打开程序文件, 检查文件头, 把参数放进新程序的数据内存, 然后在
调用者的任务与栈上运行解释器, 直到程序退出. 这相当于 Linux 中 ``fork()``、
``execve()`` 与 ``wait()`` 合在一起: 没有进程, 程序不与调用者并发运行.
不含 ``/`` 的程序名在 /bin 中查找.

代码不复制进 SRAM. 程序文件在运行期间一直打开, 解释器每取一条指令都经
文件系统的 ``peek()`` 读出一个字节, Flash 中的 /bin 与 EEPROM 中的 lxfs
都提供这一操作. 一个程序在 SRAM 中只占解释器的状态与数据内存, 约 220
字节, 与程序的长短无关. 这一做法取代了 Linux 装入程序时的 ``mmap()``.

参数的布局沿用 Linux 新进程的栈: 各参数字符串与以 0 结尾的 argv 数组放在
数据内存末尾, 程序开始时数据栈上是 argc 与 argv.

程序可以再 ``exec()`` 另一个程序, shell 就是这样运行命令的. 嵌套最多两层,
即 sh 与 sh 运行的命令, 两台虚拟机的状态是静态分配的. 描述符表为全部程序
共享, 与 Linux 中 ``fork()`` 之后父子进程共享打开的文件相同, sh 的重定向
因此对 sh 运行的程序生效.

程序因故障停止时, 内核写一条 ``vm fault N`` 日志, ``exec()`` 返回 128 加
故障号, 与 shell 中被信号终止的进程的退出码写法相同.


init 与 sh
==========

内核不再带有 shell (提交 392ed96). 开机后 init 任务把 /dev/ttyACM0 打开为
0 号与 1 号描述符, 然后运行 /bin/sh; sh 退出后, init 隔一秒重新运行 sh.
这与 Linux 以 ``init=/bin/sh`` 启动相同.

sh 读取终端交来的整行, 按空格切分为参数, 以 exec 系统调用运行第一个词所指
的程序. ``> 文件`` 与 ``>> 文件`` 以 dup2 把标准输出接到文件上, 程序结束
后从 3 号描述符恢复. 找不到程序时回答 ``sh: 名字: not found``, 其他错误以
错误码报告.


/proc
=====

ps、dmesg 与 uptime 需要任务状态、内核日志与运行时间, 这些数据在内核中.
与 Linux 相同, 内核把这些数据以文本文件的形式放在 /proc 中, 程序只需读出
(提交 056b7bd):

  ==============  ============================================
  文件            内容
  ==============  ============================================
  /proc/tasks     每个任务一行: 编号、状态与栈余量
  /proc/kmsg      内核日志, 由旧到新
  /proc/uptime    运行秒数与其中的空闲秒数, 各带两位小数
  ==============  ============================================

/proc/uptime 的格式与 Linux 相同. 文本在读取时逐行生成, 读者可以按任意
大小分次读取.


编写一个程序
============

程序以汇编写成, 放在 Leonix_coreutils 的 src/ 中, 在 Makefile 的 PROGRAMS
中加入名字即可. 一个最小的程序::

  ; hello: 输出一行
  	call setargs
  	lit hello_text
  	call puts
  	lit 0
  	sys exit

  hello_text:
  	.str "hello\n\0"

  	.include "../lib.s"

lib.s 提供参数、字符串、十进制输出与错误信息等例程, 每个程序在末尾包含
lib.s, 程序自己的第一条指令因此就是入口. 汇编语法见 lxasm.py 的文件头.

内核编译时运行 Leonix_coreutils 的 make, 再以 tools/mkromfs.py 把 build/
中的全部程序打包为 /bin.


栈与存储
========

sh 与 sh 运行的程序都在 init 任务的 318 字节栈上, 两层解释器与第二层的系统
调用叠加在一起. 第一次上板时, ps 读取 /proc 的路径使余量降到 3 字节. 内核
随后把 ``sys_write()`` 的复制缓冲区与 /proc 各行的生成函数移出公共调用
路径, 把 exec 的路径与参数暂存区改为静态, 并把栈由 288 字节增至 318 字节,
占满 .noinit 的剩余空间. 2026-10-11 连续运行各命令之后, 最低余量为 66
字节.

按 ``avr-size``, 解释器 kernel/vm.o 为 2244 字节, exec 与系统调用 1386
字节, /proc 1108 字节, /bin 的 10 个程序共 3736 字节, 其中 sh 738 字节.
映像的 text 为 23718 字节, ``__bss_end`` 为 0x0743.


测试
====

``make check`` 以汇编器编出 tests/vm/ 中的程序, 在开发机上运行解释器:
算术、16 位常数、逻辑右移、有符号比较、muldiv、循环、函数调用、内存与
write 系统调用, 以及向代码写入、栈下溢、除以零、越过数据内存四种故障.

2026-10-11 在板子上:

- ``ls /bin`` 列出 10 个程序, ``cat /bin/ls`` 读出字节码.
- echo、cat、ls、rm、df、ps、dmesg、uptime 与 help 的输出正确, uptime
  显示的空闲比例与液晶屏一致.
- ``>`` 与 ``>>`` 重定向, 未知命令, 空行, 超过 6 个词.
- 向 /bin 写入返回 EROFS.
- 连续运行 17 次 ps, sh 未退出, 也没有虚拟机故障. 第一版 sh 每运行一条
  命令就在数据栈上留下退出码, 约 16 条之后会溢出, 该错误在上板之前修正.


尚未解决的问题
==============

- 还没有从电脑把程序写入 lxfs 的办法. 终端的行规程会改写控制字符, 写入
  二进制文件需要原始模式或一种文本编码.
- 程序只能以汇编编写, 没有编译器.
- 没有进程, 程序不能与 shell 并发运行, 也没有管道.
- 解释器、驱动与内核仍是原生代码, 一个内核缺陷照样可以破坏一切.
